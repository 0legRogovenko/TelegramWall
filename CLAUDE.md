# TelegramWall — контекст для Claude

Telegram-бот: агрегатор публичных каналов с AI-саммари/дайджестами (@tgwallbot).
Общение с владельцем — по-русски. Лицензия AGPL-3.0.

## Проверка и деплой

```bash
venv/bin/python -m pytest tests/ -q
venv/bin/python -m flake8 src tests main.py auth_userbot.py scripts
```

Оба должны быть чистыми перед каждым коммитом. Пуш в `main` = деплой:
бот живёт в GitHub Actions (`bot.yml`), пуш перезапускает его. Проверка
прода: `gh workflow run healthcheck.yml`, в логе job'а искать
`OK — last seen N min ago`. Логи работающего бот-job'а недоступны, пока
job не завершён/отменён — читать можно только завершённые прогоны.

## Архитектура: один процесс, один поток

`main.py` запускает Flask (waitress) + PTB-бот + Telethon-юзербот на **одном
asyncio-потоке**. Любой блокирующий вызов (БД, Anthropic) на горячем пути —
только через `asyncio.to_thread`, иначе встаёт вся доставка.

- Юзербот **читает** публичные каналы, не вступая в них → live-пушей от
  Telegram НЕТ, единственный источник постов — опрос (`_poll_channels`).
- Бот **не может форвардить** из каналов (он не участник). Медиа: юзербот
  скачивает → бот заливает от себя → Bot API `file_id` кэшируется на пост.

## Грабли, на которые уже наступали (не повторять)

1. **Telethon `.photo`/`.video`/`.document` пролезают в веб-превью ссылки.**
   Текстовый пост со ссылкой на статью классифицировался как фото (og:image).
   Тип медиа определять ТОЛЬКО по `message.media` (см. `_get_media_type`).
2. **Опрос не бить пачками.** N запросов истории подряд каждые 30с с одного
   аккаунта → флуд-лимиты, которые Telethon по умолчанию МОЛЧА спит
   (наблюдали эффективный период опроса 27 минут при чистых логах).
   Запросы размазаны по циклу, `flood_sleep_threshold = 10`.
3. **`get_messages(limit=N, min_id)` возвращает N НОВЕЙШИХ** — бэклог сверх N
   терялся навсегда (курсор перепрыгивал). Догон — только
   `iter_messages(reverse=True, min_id=..., limit=cap)`: от старых к новым,
   излишек доживает до следующего цикла.
4. **Интервал крона `bot.yml` держать сильно меньше `timeout-minutes`.**
   Когда они были равны (5ч/300м), каждое опоздание крона GitHub (до 2ч,
   тики теряются) было простоем минута в минуту: 226 мин за 4 дня незаметно.
5. **SQLite vs Postgres в миграциях.** `_run_migration` глотает ошибки;
   `SERIAL`/`NOW()` молча падают на SQLite. Новые ТАБЛИЦЫ создаёт
   `create_all` из моделей — в `_run_migration` только `ALTER TABLE`
   для колонок в уже существующих таблицах.
6. **Подпись к медиа ≤1024 видимых символов**, включая заголовок с названием
   канала (до 128 симв.) — бюджет считать динамически
   (`_caption_text_budget`), иначе `MEDIA_CAPTION_TOO_LONG` и медиа теряется.
7. **PTB-таймауты по умолчанию (read 5s) убивают многомегабайтные заливки**
   ПОСЛЕ того, как Telegram принял сообщение → дубль поста. Для медиа —
   явные `read/write_timeout=120`.
8. **i18n-ключи выбираются тернарниками** (`t("kb_x_on" if ... else
   "kb_x_off")`) — наивный grep даёт ложные «мёртвые ключи». Не удалять без
   проверки исполнением.
9. **`err_types` в `report.py` — явный список.** Новый тип `error_*` в
   metrics.py обязан попасть туда, иначе отчёт его не считает
   (`LIKE 'error_%'` нельзя: `_` — SQL-wildcard).
10. **Всё, что уходит в Telegram с `parse_mode="HTML"`, экранировать** через
    `html.escape` — сырой текст исключения с `<html>` внутри валит всё
    сообщение (Telegram отвергает целиком).

## Инварианты доставки

- Каждый пост — отдельным сообщением (сводок-пачек НЕТ, пользователь их
  явно отверг). Порядок от старых к новым; на (user, channel) — по порядку
  через `_in_flight`.
- Альбом (`grouped_id`) = один Post; склейка через БД, не память (рестарт
  каждые ~2ч не должен рвать альбом). Единственная задержка доставки —
  20с grace, чтобы подпись альбома с позднего элемента успела приклеиться.
- Сбой в середине пачки: доставленное не дублируется, остаток —
  в `pending_posts` (переживает рестарт, добивается на старте).
- SIGTERM-хук (`flush_buffer_on_shutdown`) сохраняет буфер, in-flight
  записи и буфер метрик. Рестарты — штатный режим, не исключение.
- Авто-саммари media-поста: саммари едет ПОДПИСЬЮ к медиа, не вместо него.

## Метрики и мониторинг

- `metrics.record()` — только append в память, НИКОГДА не БД и не raise
  (горячий путь). БД — `flush()`/`heartbeat()` через `to_thread`.
- Сторож — внешний (`healthcheck.yml`, крон 30 мин), читает
  `bot_health.last_seen_at`. `alert_sent_at` пишется ТОЛЬКО после реально
  доставленного алерта. Пороги — repo Variables, не `.env`.
- Дневной отчёт: сначала claim (`last_report_on`), потом отправка — иначе
  сбой отметки = спам отчётом весь день.

## Тесты

Общая in-memory SQLite на всю сессию: `commit()` из одного теста ВИДЕН
другим — чистить состояние autouse-фикстурой, не полагаться на rollback.
`conftest.patch_db_session` патчит `db_session` в каждом модуле хендлеров
поимённо + `metrics.SessionFactory` — новый модуль с БД-доступом добавлять
в этот список, иначе он молча пишет в бестабличный движок и «покрыт» только
на вид.

## Прочее

- Модель: `claude-haiku-4-5`, `thinking={"type": "disabled"}` обязателен,
  текст из ответа — через `_text_of()`. Цены в `metrics.py` — хайковские.
- Админы (`TELEGRAM_ADMIN_IDS`): Pro навсегда, `/admin`, `/report`,
  `/block @канал`, `/unblock`.
- Чёрный список каналов: механизм в `src/services/blocklist.py`
  (env `BLOCKED_CHANNELS` закреплён, БД — оперативно). Список НЕ наполнять
  кодом — какие источники блокировать, решает оператор.
- `promo/` в `.gitignore` — маркетинговые черновики, не коммитить.
- Секреты — GitHub Secrets (`gh secret set`); `.env` только локально.
